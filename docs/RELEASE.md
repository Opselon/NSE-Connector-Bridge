# Release

## 1. Release process

1. Bump `BRIDGE_VERSION` in `nse_bridge/__init__.py`.
2. Re-run the generators (CI enforces both with `--check` / `diff`):
   ```bash
   python scripts/write_version_info.py
   python scripts/export_openapi.py docs/openapi.json
   ```
3. Run the Linux gate locally (or wait for CI on the PR):
   ```bash
   ruff check .
   ruff format --check .
   python -m mypy nse_bridge
   python -m pytest tests/unit tests/integration -q
   ```
4. Merge only after explicit user approval (branch protection /
   project rule: never merge without it). Tag the release from `main`:
   `v1.2.3` for stable, `v1.2.3-rc.1` for a prerelease.
5. CI's `release` job (tags only) builds the exe on Windows,
   checksums it, signs every artifact with Ed25519 (P1-6 — when the
   GitHub Actions secret `NSE_BRIDGE_RELEASE_SIGNING_KEY` is set;
   without it the release ships unsigned and the job says so),
   writes the manifest, and attaches all files to the GitHub release
   with generated notes:
   - `NSE-MT5-Bridge.exe` (single-file, Windows x64, `console=False`)
   - `NSE-MT5-Bridge.exe.sha256` (`"<sha256>  NSE-MT5-Bridge.exe"`)
   - `NSE-MT5-Bridge.exe.sig` (base64 Ed25519 over the exe bytes)
   - `NSE-MT5-Bridge-Setup-<version>.exe` (per-user Inno Setup
     installer, no admin; built from `windows/NSE-MT5-Bridge.iss`
     in the `build-windows` job — see docs/BUILD.md §3)
   - `NSE-MT5-Bridge-Setup-<version>.exe.sha256`
   - `NSE-MT5-Bridge-Setup-<version>.exe.sig`
   - `NSE-MT5-Bridge-<version>-windows-arm64.exe` (native ARM64,
     core-only) + `.sha256` + `.sig`
   - `NSE-MT5-Bridge-<version>-macos-x64.dmg` + `.sha256` + `.sig`
   - `NSE-MT5-Bridge-<version>-macos-arm64.dmg` + `.sha256` + `.sig`
   - `NSE-MT5-Bridge-<version>-linux-x64.tar.gz` + `.sha256` + `.sig`
   - `NSE-MT5-Bridge-<version>-linux-arm64.tar.gz` + `.sha256` + `.sig`
   - `release-manifest.json`
     (`{name, version, tag, commit, platform: "windows-x64",
     platforms: ["windows-x64", "windows-arm64", "macos-x64",
     "macos-arm64", "linux-x64", "linux-arm64"],
     files: [{name, sha256, size_bytes, platform, signature}]}` — every artifact
     is listed with its real SHA-256, its platform, and — on a signed
     release — its base64 Ed25519 signature; the setup exe
     sits alongside the exe)
6. Verify a download before announcing it:
   ```powershell
   (Get-FileHash NSE-MT5-Bridge.exe -Algorithm SHA256).Hash
   # must equal the .sha256 sidecar and the manifest entry
   ```
   and, on a signed release, the Ed25519 signature (same bytes the
   updater verifies — see the signing section in §5):
   ```powershell
   python scripts/sign_release_artifact.py --verify `
     --public-key-file nse_bridge/update_public_key.b64 `
     --manifest release-manifest.json NSE-MT5-Bridge.exe
   ```

Users on Windows can install/upgrade directly from GitHub Releases
with `scripts/install.ps1` (documented in docs/INSTALLATION.md): it
resolves the latest release of the requested channel (`-Channel
Stable|Prerelease`, or pin `-Version`), verifies SHA-256 three ways
(manifest entry + `.sha256` sidecar + recomputed file hash), and
installs the setup exe (default, `-Silent` supported) or just the
standalone exe (`-Portable`), with `-InstallDir`, `-Force`,
`-VerifyOnly` and honest exit codes 0–7 (0 success or verified ·
1 usage error · 2 unsupported Windows version/arch · 3 GitHub
unreachable · 4 expected artifact missing · 5 checksum mismatch ·
6 installer failed · 7 post-install verification failed — see the
header of `scripts/install.ps1`). A release published without a
signature is reported as such, not silently accepted: the
signature-gap is stated in the script output where the verification
summary prints.

Stable and prerelease are separate by tag name: any tag containing
`-` (e.g. `v1.2.3-rc.1`) is published as a prerelease; `v1.2.3` is
stable. The two are never mixed in one release. No release is ever
cut from an untested build — the `release` job needs
`build-windows`, `build-windows-arm`, and `build-unix` (which need
`test-linux`); each build job ran the gates and a frozen-binary smoke
on its own runner.

## 2. What a release contains

- The exe (version metadata + manifest embedded; see docs/BUILD.md §3).
- The Windows installer (`NSE-MT5-Bridge-Setup-<version>.exe`,
  per-user, no admin) plus its SHA-256 sidecar — same treatment as
  the exe; see docs/BUILD.md §3.
- The cross-platform artifacts (v1.3.0): Windows ARM64 portable exe
  (core-only), macOS `.dmg`s (x64 + arm64, `.app` inside), Linux
  tarballs (x64 + arm64) — each with its own SHA-256 sidecar; see
  docs/INSTALLATION.md for what runs where. Only the Windows x64
  build can attach to MT5; every other target reports
  `MT5_WINDOWS_REQUIRED`.
- SHA-256 checksum + manifest, generated by
  `scripts/write_release_manifest.py` from the real built files —
  never hand-written, never invented.
- Release notes (auto-generated by GitHub from merged PRs) plus the
  human-facing draft in `docs/RELEASE-NOTES-1.3.0.md` (v1.3.0 only).
- The updater authority is CONTRACT v1 §3.5 `releases/latest`
  (version, download_url, sha256, size_bytes, min_connector_version,
  Ed25519 signature, released_at); GitHub Releases remains the
  artifact host behind that endpoint.

Consumers of that artifact set: `scripts/install.ps1` is the
documented one-command installer/upgrader over GitHub Releases
(SHA-256 manifest + sidecar + file triple verification; see §1
step 6 above and docs/INSTALLATION.md).

## 5. Known gaps (explicit, not hidden)

1. **Icon — CLOSED.** The original NSE-branded `.ico` is generated
   by `scripts/make_icon.py` into `assets/icon.ico`, wired into both
   the exe (`bridge.spec:65`) and the installer
   (`SetupIconFile=..\assets\icon.ico`), and gated by
   `tests/unit/test_icon_asset.py`. Regenerate via the script; never
   hand-edit the binary.
2. **Release signing (P1-6) — CLOSED.** `scripts/sign_release_artifact.py`
   (Ed25519/base64, exactly the signatures `verify_artifact` accepts)
   + a signing step in the `release` job + the provisioned public key
   in `nse_bridge/update_public_key.b64` (bundled into the frozen exe
   via `bridge.spec`). The private key lives ONLY in the GitHub
   Actions secret `NSE_BRIDGE_RELEASE_SIGNING_KEY` (set it before the
   first signed release — until then releases ship unsigned, as
   v1.4.0 did, and the job says so) and in the operator backup at
   ParsPack FTP `/opselon-passwords/nse-bridge-release-signing-private-key.pem`
   (byte-verified on upload). It never appears in chat, memory, the
   repo, a PR, or a log. The updater can now install a signed
   release; an unsigned release still refuses fail-closed
   (`SIGNATURE_MISSING`).
   **The "runtime safeguard warning" reported as blocking P5b has no
   textual trace anywhere in the repo** (`git grep -i safeguard`:
   zero matches) and could not be verified or explained from code;
   the pipeline above proceeds per the P5b design instead.
3. **Telemetry delivery gap** (CONTRACT v1 §4.2): no diagnostics
   upload endpoint. The local pipeline is complete; the sink is
   inert (`NullDiagnosticsSink`). ERROR/WARN events queue locally
   (128 items, 1 h TTL) and age out if no endpoint ever appears.
   Platform-side dependency — docs/PLATFORM-GAPS.md §2.
4. **`modify_pending` capability gate closed** (§17.4): live proof at
   market open + published minimum `connector_version` still owed.
   Until then the op is rejected as `UnsupportedOperation`.
5. **ARM64 — core-only since v1.3.0 (was: unsupported).** Native
   ARM64 builds ship for Windows (portable exe), macOS (`.dmg`), and
   Linux (tarball); they run the bridge core and report
   `MT5_WINDOWS_REQUIRED` for terminal attach. Trading still needs
   the Windows x64 build. See docs/COMPATIBILITY.md §2.
6. **15 pre-existing ruff findings — FIXED (A1).** The whole-repo
   gate `ruff check .` passes (ruff 0.17.5): unused imports removed
   (`engine/market.py`, `engine/registry.py`), dead local removed
   (`engine/risk.py`), duplicate `SymbolInfoModel.session_deals`
   field removed (`mt5/types.py`), `datetime.fromisoformat` "Z"
   handling simplified (`timeutil.py`, Python ≥3.11 parses "Z"),
   import/`__all__` sorting fixed, and the five intentional
   broad-`except` sites documented with `# noqa: BLE001` reasons
   (diagnostics probes, boot thread, MT5 field accessor). The
   import order in `engine/__init__.py` was verified not to change
   `docs/openapi.json` (re-export diff is empty).
7. **Windows CI not yet executed** on this branch; the frozen exe has
   never been built from this ref. The `build-windows` test step
   failed at head `3f0950c` with the cause undiagnosed (job logs
   return 403 from this environment; no Linux simulation reproduced
   it). A1 made the next failure identifiable — both test steps emit
   `--junitxml=test-results.xml -rf` and upload the XML on failure —
   and hardened the nested-pytest honesty proof (UTF-8 child output,
   `TimeoutExpired` becomes a named failure). First green
   `build-windows` run is required before any tag.
8. **Live Platform unverified** (see §3). No release should be
   announced as "verified against the live Platform" until the
   Platform side deploys the contract (PR #107) and a live
   enrolment/sync/command round-trip is observed.
9. **Backtest intentionally excluded** (clarification #2). There is
   no backtest subsystem, screen, or status — by design, not by
   omission. Do not add one in this phase.
