# Build

## 1. Requirements

- Python 3.12 or 3.13 (3.14 is untested on dev machines with broken
  numpy/pip — use a clean 3.12/3.13). CI uses 3.13.
- Windows 10/11 x64 for the packaged exe (MT5 + the MetaTrader5
  wheel are Windows-only). Linux builds/runs the pure-Python parts
  (tests, mock server, OpenAPI export) but cannot run MT5 tests.
- Pinned dependencies: `requirements.txt` (runtime + build) and
  `requirements-dev.txt` (adds pytest, pytest-asyncio, ruff, mypy,
  bandit, pip-audit). `pyproject.toml` carries the same pins as the
  `[project]` dependencies.

## 2. Local development

```bash
py -3.13 -m venv .venv
.venv/Scripts/python -m pip install -r requirements-dev.txt

# Lint + tests (the CI Linux gate, runnable on Linux too)
ruff check .
ruff format --check .
python -m mypy nse_bridge
python -m bandit -r nse_bridge --skip B101,B110,B311,B404 -q
python -m pip_audit -r requirements.txt -r requirements-dev.txt
python -m pytest tests/unit tests/integration -q

# Run the bridge (dev)
.venv/Scripts/python -m nse_bridge            # GUI on http://127.0.0.1:8788
.venv/Scripts/python -m nse_bridge --gui none # headless
.venv/Scripts/python -m nse_bridge --console  # foreground console service, no GUI
.venv/Scripts/python -m nse_bridge --diagnostic  # diagnostic console mode

# Query the RUNNING bridge (never boots a second instance)
.venv/Scripts/python -m nse_bridge status --json
.venv/Scripts/python -m nse_bridge health --json
.venv/Scripts/python -m nse_bridge diagnostics --json
.venv/Scripts/python -m nse_bridge mt5 list --json

# Local-processing benchmark (CI bench job; baselines in docs/PERFORMANCE.md)
.venv/Scripts/python scripts/bench_local_api.py --samples 400 --out bench-report.json

# Validate docs (links, command-count drift, OpenAPI freshness) — CI docs gate
.venv/Scripts/python scripts/check_docs.py

# Mock NSE server (CONTRACT v1) for integration tests / manual runs
.venv/Scripts/python scripts/mock_server.py   # WS :9099, REST :9098

# Re-export the OpenAPI schema from the registry (CI enforces freshness)
.venv/Scripts/python scripts/export_openapi.py docs/openapi.json
```

CLI flags (`nse_bridge/main.py`, `build_parser()`):
`--host` (default 127.0.0.1), `--port` (default 8788), `--gui
auto|webview|browser|none`, `--no-connect` (skip MT5 auto-connect at
boot), `--diagnostic` (diagnostic console mode — see §4), `--console`
(foreground console service: attach/allocate a console, GUI off,
clean Ctrl+C shutdown). Query subcommands
`status|health|diagnostics|mt5 list` (add `--json`) talk to the
RUNNING bridge and dispatch BEFORE any serve setup — they never boot
a second instance (`nse_bridge/cli.py`; exit codes 0 ok · 1 usage ·
2 another instance already running · 3 bridge not running · 4
operation failed · 5 server error).

## 3. The exe (`bridge.spec`)

PyInstaller single-file build, x64:

```bash
.venv/Scripts/python -m PyInstaller bridge.spec --noconfirm --clean
# → dist/NSE-MT5-Bridge.exe
```

Spec contents:

- **Entry:** `run_bridge.py` → `nse_bridge.main:main`.
- **`console=False`** — no console window in production. Diagnostics
  use `--diagnostic` (see §4).
- **Version metadata:** `version="version_info.txt"` — generated
  from `nse_bridge.BRIDGE_VERSION` by
  `scripts/write_version_info.py`. After every version bump, re-run
  the script; CI enforces freshness with `--check`.
- **Windows manifest:** `manifest="windows/NSE-MT5-Bridge.exe.manifest"`
  — also generated by `write_version_info.py`. `asInvoker` (no UAC
  prompt; the Bridge runs unprivileged), `dpiAware`, `longPathAware`,
  Windows 8.1/10 in `supportedOS`.
- **Icon:** `icon="assets/icon.ico"` (bridge.spec:65) — the original
  NSE-branded asset, generated by `scripts/make_icon.py` (re-run the
  script to regenerate; never hand-edit the binary). Its presence and
  non-triviality are gated by `tests/unit/test_icon_asset.py`, and
  the installer carries the same asset (`SetupIconFile`, see below).
- **Bundled data:** `nse_bridge/gui/static` (Control Center HTML).
  Hidden imports cover `MetaTrader5`, `numpy`, `pywebview`,
  `websockets`, `uvicorn`, `loguru`, `webview.platforms`.
  Excluded: `tkinter`, `matplotlib`, `pandas`, `pytest`.

Smoke-check a built exe. `--help` exits before any server or GUI
starts, so it is safe on a runner; the deeper smoke is
`scripts/smoke_exe_local.ps1`, which boots the frozen exe HEADLESS on
Windows and asserts real behavior: `/health` reaches `ready`, `/ui`
serves 200, the CLI JSON subcommands (`status|health|mt5 list --json`)
parse and exit 0, and a second launch refuses with exit 2
(single-instance). CI's `build-windows` job runs this script against
the built exe (see §6). On a frozen exe, note startup takes a few
seconds longer than a dev run — the smoke script polls `/health`
instead of sleeping a fixed time.

### The Windows installer (`windows/NSE-MT5-Bridge.iss`)

Inno Setup 6 script, built by the `build-windows` CI job from the
built exe — so it is proven to compile on every PR, not just on
tags:

```powershell
iscc /DAppVersion=1.0.0 /DAppVersionInfo=1.0.0.0 windows\NSE-MT5-Bridge.iss
# → dist\NSE-MT5-Bridge-Setup-1.0.0.exe
```

- **Per-user install** (`PrivilegesRequired=lowest`): no admin, no
  UAC; installs to `%LOCALAPPDATA%\Programs\NSE MT5 Bridge`.
  Config/secrets live under `%LOCALAPPDATA%\NSE MT5 Bridge` and are
  created by the Bridge itself at runtime — the installer ships
  only the single exe and never touches user data (uninstall leaves
  config intact).
- **Branded setup icon:** `SetupIconFile=..\assets\icon.ico`
  (windows/NSE-MT5-Bridge.iss:56) — same generated asset as the exe.
- **x64 only** (`ArchitecturesAllowed=x64os`); Windows 10+.
- Start Menu shortcut + optional (unchecked) desktop shortcut,
  post-install launch option, standard uninstaller entry. The
  stable `AppId` GUID is never changed — same AppId upgrades in
  place. If the Bridge is running, the installer asks to close it
  first (`CloseApplications=yes`).
- Version comes from `BRIDGE_VERSION` (CI passes it as
  `/DAppVersion`); `AppVersionInfo` is the numeric 4-part quad the
  version resource needs. Branded setup icon (see above).

## 4. Diagnostic mode (`--diagnostic`)

`NSE-MT5-Bridge.exe --diagnostic` (or `NSE_BRIDGE_DIAGNOSTIC_MODE=1`,
or `diagnostic_mode: true` in config.json) enables:

- DEBUG telemetry events (otherwise dropped silently;
  ARCHITECTURE-CONTRACT §8),
- DEBUG log level (only when the configured level is still the
  default `INFO` — an explicitly set level is respected),
- on a frozen Windows build, a console window allocated
  best-effort (`AllocConsole` via ctypes, win32 + frozen only;
  failures swallowed — diagnostic mode works with or without it).
  On Linux/dev runs the flag is a no-op for the console part (a
  console already exists).

The flag is unit-tested (`tests/unit/test_diagnostic_flag.py`:
parses, defaults off, combines with other flags).

## 5. Versioning

- Single source of truth: `BRIDGE_VERSION` in `nse_bridge/__init__.py`
  (currently `1.0.0`).
- `scripts/write_version_info.py` derives `version_info.txt`
  (VSVersionInfo: FileVersion/ProductVersion, CompanyName `Opselon`,
  ProductName `NSE MT5 Bridge`) and
  `windows/NSE-MT5-Bridge.exe.manifest` from it. Never hand-edit the
  generated files.
- Releases use semver tags: `v1.2.3` (stable), `v1.2.3-rc.1`
  (prerelease). See docs/RELEASE.md.
- `min_connector_version` in `releases/latest` is honored by the
  updater: a release requiring a newer connector than the running
  one is refused (`MIN_VERSION_NOT_SATISFIED`).

## 6. CI (`.github/workflows/build.yml` + `.github/workflows/docs.yml`)

`build.yml`: four jobs — `test-linux` → `build-windows` (chained),
`bench` (main/dispatch only), `release` (tags only).

| Job | Runs | Steps |
|---|---|---|
| `test-linux` | ubuntu-latest | `ruff check .` · `ruff format --check .` · `mypy nse_bridge` · `bandit` + `pip-audit` · `write_version_info.py --check` · OpenAPI freshness (`export_openapi.py` + `diff`) · `pytest tests/unit tests/integration -q --junitxml=test-results.xml -rf` (junit uploaded on failure) · marker-count visibility |
| `build-windows` | windows-latest | same lint + types + security + same unit/mock-integration suites on Windows (proves Windows imports work; junit uploaded on failure) · `pyinstaller bridge.spec` · **headless frozen-exe smoke (`scripts/smoke_exe_local.ps1`): boots the exe, `/health` ready, `/ui` 200, CLI JSON `status/health/mt5 list` parse + exit 0, second launch exits 2** · `iscc windows\NSE-MT5-Bridge.iss` (Inno Setup installer) · upload exe + setup exe |
| `bench` | main pushes, tags, manual dispatch (NOT on PRs — keeps PR checks fast) | `python scripts/bench_local_api.py --samples 400 --out bench-report.json`; report uploaded as an artifact. Baselines live in docs/PERFORMANCE.md — numbers are machine-specific, compare like with like |
| `release` | windows-latest, tags `v*` only | download exe + setup exe · `write_release_manifest.py --setup ...` (SHA-256s + manifest) · attach exe + setup exe + both `.sha256` sidecars + manifest to the GitHub release (`prerelease` iff the tag contains `-`, generated notes) |

`docs.yml` is the docs-only gate (`.github/workflows/docs.yml`): the
main build workflow paths-ignores docs, which used to leave docs-only
changes with no signal at all. It runs `scripts/check_docs.py` —
relative-link integrity across README.md + every docs/*.md,
command-count drift against the parsed registry (README,
docs/index.html, docs/COMMAND_REFERENCE.md), and `docs/openapi.json`
freshness.

The real-MT5 e2e suite is NEVER run in CI: GitHub-hosted runners
have no MT5 terminal, and a required-MT5 test fails loudly without
one. E2E is manual, Windows-with-MT5-only (docs/RELEASE.md).

Triggers (`build.yml`): push to `main` / `refactor/**`, tags `v*`,
PRs to `main`, manual dispatch.

## 7. Known build gaps

- **Icon: closed.** The original NSE-branded `.ico` is generated by
  `scripts/make_icon.py` into `assets/icon.ico` and wired into both
  the exe (`bridge.spec`) and the installer (`SetupIconFile`);
  integrity gated by `tests/unit/test_icon_asset.py`. To change the
  icon, edit the generator and re-run it — never hand-edit the
  binary.
- **ARM64 unsupported** (see docs/COMPATIBILITY.md): x64 only; no
  ARM64 build is published, and the unsupported path must produce a
  clear message, not a broken binary.
- **Lint / format / types / security are whole-repo gates now (A1,
  spec §20):** `ruff check .` (the 15 pre-existing findings are
  fixed, not waived), `ruff format --check .`, `mypy nse_bridge`
  (pydantic plugin; see `pyproject.toml`), `bandit -r nse_bridge`
  and `pip-audit` on both requirement files. Bandit skips four
  Low-severity rules only (`B101,B110,B311,B404`), each reviewed and
  documented in `.github/workflows/build.yml`.
- **Windows CI test failure (3f0950c) is still undiagnosed** — the
  `build-windows` test step failed with job logs unreachable (403),
  and no Linux simulation reproduced it. A1 hardened the most
  Windows-fragile test path (the nested-pytest honesty proof:
  UTF-8 child output, `TimeoutExpired` becomes a named failure) and
  made the next failure identifiable: both test steps now emit
  `--junitxml=test-results.xml -rf` and upload the XML on failure,
  so the failing test names are visible without log access. The root
  cause still needs a green-or-red Windows run with the artifact.
- **The frozen exe itself is only proven by Windows CI.** This Linux
  VM cannot run PyInstaller against the Windows-only dependency set
  (MetaTrader5 wheel, pywebview backends); `bridge.spec` validity on
  Windows is proven by the `build-windows` job, not locally.
